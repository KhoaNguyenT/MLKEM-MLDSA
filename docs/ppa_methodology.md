# Verification and PPA methodology

## Tool roles

### Verilator

Use Verilator for fast, reproducible iteration:

- lint each block-specific source list;
- compile synthesizable RTL and its dedicated testbench;
- run functional and differential simulations;
- capture seeds, vectors, cycle counts, assertions, and logs;
- reject a target before implementation if its required simulation fails.

Do not compile the entire `Mydev_before` tree as one unit because it contains duplicate
module names and alternative implementations.

### Vivado 2024.2

Use Vivado 2024.2 as the authoritative FPGA implementation/PPA flow:

- synthesize with an explicit top, source list, FPGA part, and XDC;
- run implementation through route, not synthesis-only, for final timing claims;
- report LUT, FF, DSP, BRAM/URAM, WNS, TNS, achieved clock, and implementation status;
- report power only with its activity source and assumptions;
- retain tool/version, part, strategy, constraints, warnings, and raw reports.

Local executable:

`D:\vivado\Vivado\2024.2\bin\vivado.bat`

## Cross-tool contract

For a given target, Verilator and Vivado must use the same:

- synthesizable source list and selected alternative modules;
- top-level RTL parameters and preprocessor defines;
- reset polarity and clocking assumptions;
- input vectors and expected observable behavior where applicable.

Vendor primitives may require a simulation model or a portable wrapper. Any divergence
between simulation and implementation source sets must be documented.

## Baseline comparison rules

- Never overwrite an earlier report directory.
- Compare the same FPGA part, constraints, clock, workload, and tool version.
- Report ML-KEM KeyGen, Encaps, and Decaps separately when the design supports them.
- Include cycles, latency, throughput, area, timing, and power/energy assumptions.
- Label historical results as unverified until regenerated by the current scripts.
- Keep FIPS correctness, functional simulation, and PPA acceptance as separate gates.
